From route to row and back: transcript

From route to row and back: one request, five floors, and the shape of the answer on each.

A request arrives: a GET to /api/tasks/7. The route file only matches. Path and method in, a controller out. No logic here.

The controller speaks HTTP. It reads the id from the request, and turns the text "7" into a number. Then it asks the model for the task, and waits. It never writes SQL.

The model is the only floor that knows there is a database. One method per operation. Here: findById, with the number 7. It never touches the request or the response.

Below the model, the pool. Created once, at start-up, from the DATABASE_URL in the environment. It keeps a few connections open, and lends one to each query. No new login per request. Create it inside a handler, and connections pile up until the database says: too many clients.

The query leaves in two parts. The SQL text, with a placeholder: $1. And the values: an array holding 7, travelling apart. The database compiles the text first. Only then does the 7 drop into the slot.

Why apart? Suppose the input is a trick string that is always true. Glued into the text, it becomes SQL, and the query matches every row. Sent as a value, it is just an odd string that matches nothing. A template literal is still gluing. Only a placeholder keeps input out of the SQL.

One request, several changes that belong together? Take one client from the pool. Each pool query may use a different connection, so BEGIN and COMMIT would never meet. Use that one client from BEGIN to COMMIT. ROLLBACK on an error, and always give it back.

Now the answer climbs back. The driver hands the model an array of rows. The model takes the first one: id 7, Draft project plan.

But a row is not the answer yet. The model maps it, in one place. snake_case column names become camelCase keys. user_id turns into userId. Dates become ISO strings. And only the fields you list leave the model, so a password hash never leaks by accident.

Now the controller holds a plain object. It picks the status, 200, and sends JSON.

Ask for task 999 instead. No row comes back. The model does not fail. A missing row is a normal answer: null. The controller turns null into a 404. Only the controller speaks HTTP.

Because the model is handed its database, a test can hand it a fake. No server needed. And the same method names work over MongoDB. The controller never changes.
