Render, commit, effect: transcript

Render, commit, effect: the three steps behind every change on a React screen.

One click calls setCount(count + 1) three times. The screen goes up by one, not three. To see why, picture a photo booth. The click gets a snapshot. It never sees what happens next.

A component is a function that returns what the screen should look like. Every time React calls it, that's a render. And every render is one photo. In this photo, count is frozen at 0. For this render, it's a constant. Even the click handler is stuck in its photo. It keeps seeing 0, however long it lives.

A click can't edit the photo. Each setter call just writes a note: make it 1. Three calls, three identical notes. A log straight afterwards still prints 0. When the handler returns, React reads every note and develops one new photo. count is 1. Five setters in one click still mean one render. That's batching: no half-finished photos.

Write the note differently: add one to whatever it is by then. Now the notes chain: 0, 1, 2, 3. The next photo shows 3. Use this form whenever the next value depends on the previous one.

Developing the photo is the render. It only works out what the screen should look like. Then comes the commit. React pins the photo to the wall, changing only what differs. The wall is the DOM. Watch the strip below: render, then commit. Every photo goes through both.

The flash goes off, and now effects run. An effect keeps something outside React in sync. A chat component connects to the "general" room, after the commit. Its dependency array lists the values it reads. Here, the room.

Type in a text box, and the room stays the same. React compares, sees no change, and skips the effect. Leave a value out of the array, and the effect keeps using the old one. Fix the reason, never the array.

The user switches to "travel". New photo, new commit. Before the new effect runs, React takes down the old one: disconnect from "general". Only then does it connect to "travel". Stop the old, start the new, always in that order. Close the chat, and the last cleanup runs once more. In development, StrictMode does this on purpose, to prove your cleanup really undoes your setup. Render, commit, cleanup, effect. Same order, every photo.
